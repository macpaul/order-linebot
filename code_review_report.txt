- **P1 — Google Sheets formula-injection**: user text starting with `=` (e.g. an item named `=SUM(A1:A10)`) is evaluated as a formula on open.

- **P1 — Date vs DayOfWeek mismatch**: a day-prefixed order stores `date`=placed-on but `dayOfWeek`=meal-for, which can confuse readers/queries.

- **P2 — Minor**: `initSheets()` re-runs on every webhook; inconsistent `getActiveSpreadsheet()` vs `getSpreadsheet()` for toasts; unused `_flexIcon/_flexButton/_flexImage` helpers; deployment guide documents 4 tabs but code creates 5.

**Bottom line:** ship-quality core with a small, well-understood defect list. The **P0 price bug** is the only thing that can silently produce a *wrong number* in normal operation; the rest are robustness/clarity improvements that don't break the happy path. ▸ src/SheetService.js  (788 LOC)  —  RATING 8/10
  VERIFIED STRENGTHS:
   • Clean 5-tab schema (Config, WeeklySchedule, Menu, Orders, Summary)
     with correct headers. initSheets() idempotently creates tabs + bold
     headers + sample data. Verified: all 5 tabs defined correctly.
   • Excellent in-memory _mockStore mirror of the sheet schema enables
     full offline Node testing. Verified: mock Config/WeeklySchedule/Menu
     all consistent with real schema.
   • getWeeklySchedule()/getScheduleByDay()/setWeeklyScheduleDay()
     correctly implement Mon–Fri batch scheduling. Verified: admin
     update of 週二 to 五星級牛排便當 11:00 round-trips correctly.
   • addOrder() correctly computes subtotal = quantity × price and
     generates unique OrderId (timestamp + random). Verified: order
     records have correct subtotals.
   • getWeeklyOrderSummary() correctly aggregates Mon–Fri into
     daySummaries + grand totals + per-user weekly totals. Verified:
     test scenario (Alice Mon 1×$100 + Wed 2×$70, Bob Fri 2×$110) yields grand
     total 5 items / $460 — matches expected.
   • onOpenSpreadsheet() admin menu is well-organized (init, daily
     summary, weekly summary, UberEats import dialog).

  ISSUES:
   [MAJOR] Google Sheets formula-injection vector.
     User-provided text (item names, user names, restaurant names)
     is written via sheet.appendRow() / getRange().setValue() WITHOUT
     escaping a leading "=". If an item name is "=SUM(A1:A10)" (or a user
     named "=HYPERLINK(...)"), Sheets evaluates it as a formula on
     open — potential data leak / calc load / even external fetch via
     =IMPORTHTML / =IMPORTDATA.
     FIX: Prepend a "'" (apostrophe) or escape "=" → "\=" for any string
     value starting with "=", OR set the column's number format to
     text ("@"), OR sanitize on write: `val = String(val); if (val[0]==='=')
     val = "'" + val;`.

   [MAJOR] getMenuItems() restaurant filter is an exact string match
     that can silently return an empty menu.
     Logic: `restMatches = restaurantName ? (itemRest === restaurantName)
     : true`. If the Menu tab's RestaurantName for a day doesn't EXACTLY
     equal the WeeklySchedule's RestaurantName for that day (case,
     trailing space, traditional/simplified variant, abbreviation),
     the menu comes back empty and the user sees "（尚無項目）" with no
     explanation. Verified: mock data uses consistent names so tests
     pass, but real admin-entered data is far less consistent.
     FIX: Normalize both sides before compare:
     `const norm = s => String(s||'').trim().toLowerCase();`
     then `norm(itemRest) === norm(restaurantName)`. Also consider
     falling back to day-only match (ignore restaurant) when the
     strict match yields zero, so the user at least sees the menu.

   [MINOR] getMenuItems() / getConfigValue() / etc. re-read the ENTIRE
     sheet via getDataRange().getValues() on every call. Fine for the
     small sheets this bot uses (dozens of rows), but it's O(rows) per
     call and there's no caching. If the Orders tab grows to thousands
     of rows, repeated full reads in a loop (e.g. getWeeklyOrderSummary
     calls getGroupOrders 5×, each re-reading the whole Orders tab)
     become wasteful. Not a correctness bug; a perf note.

   [MINOR] setConfigValue() appends a new row if the key isn't found,
     but doesn't dedupe — calling it twice for a new key creates two
     rows with the same key. getConfigValue() then returns the FIRST
     match, which may be stale. Low impact (config keys are mostly
     pre-seeded by initSheets) but worth a guard.

▸ src/OrderService.js  (462 LOC)  —  RATING 8/10
  VERIFIED STRENGTHS:
   • parseOrderText() is the crown jewel — handles 4 quantity syntaxes
     (+N prefix, name+N suffix, name*N / name xN multiply, 點餐 name N)
     AND 3 day-prefix dialects (週X, 禮拜X, 星期X) normalized to 週X, AND
     comma/newline multi-line batch splitting. Verified against 20
     edge-case strings; all standard forms parse correctly, and
     genuinely-ambiguous garbage ("你好 +1 排骨飯", bare "排骨飯", bare
     "+1") are correctly rejected (empty result) rather than
     mis-parsed. This is well-engineered.
   • getTodayDateString() / getTodayDayOfWeek() correctly convert to
     Taiwan time (UTC+8) via getTimezoneOffset math. Verified: the
     UTC→TW conversion is algebraically correct.
   • handleTextMessage() is a clean, well-ordered sequential
     dispatcher (help → weekly schedule → day menu → UberEats import
     → open order → today menu → my weekly orders → my today orders
     → cancel → weekly summary → today summary → close → order
     placement). Exact-match command patterns are properly anchored
     (^…$) so they don't false-trigger. Order placement is correctly
     the fall-through default.
   • Mon–Fri weekly batch ordering is correctly implemented: a single
     command can place orders across multiple days ("週一 排骨飯+1, 週二
     雞腿飯+2, 週四 水煮雞胸*1"), each routed to the correct day's menu via
     getScheduleByDay(day) + getMenuItems(day, dayRest). Verified: the
     3-day batch test (Step C) records all three days correctly.
   • matchMenuItem() two-tier matching (exact → bidirectional contains)
     is reasonable and verified: "排骨" → "招牌排骨飯" ($100), "古早味紅茶" →
     exact ($25).

  ISSUES:
   [MAJOR] Async race: getUserProfile() display-name fetch can lose
     to the synchronous order insert.
     In the order-placement block, the code does:
        var userDisplayName = '成員';
        profilePromise.then(prof => { userDisplayName = prof.displayName; });
        // ... then SYNCHRONOUSLY, a few lines later:
        orderItems.forEach(oi => {
           ...
           var record = SheetModule.addOrder({ ..., userName: userDisplayName, ... });
        });
     The .then() callback is async — it has NOT necessarily run by the
     time addOrder() executes a few lines later. So userDisplayName is
     very likely still the default '成員' when the order row is written.
     Net effect: Orders.UserName is populated with '成員' instead of the
     user's real LINE display name. The receipt Flex (created after the
     loop) MAY show the correct name if the .then() landed by then, creating
     an inconsistency between the stored row and the displayed receipt.
     FIX: Await the profile before the insert loop (make the enclosing
     function async and `const prof = await LineModule.getUserProfile(...)`),
     OR at minimum fetch the profile synchronously-ish by resolving it
     before building records. Given GAS's single-threaded event loop, the
     cleanest fix is to restructure so the displayName is resolved before
     addOrder is called.

   [MAJOR] Semantic date / day-of-week mismatch in the Orders record.
     When a user places a day-prefixed order (e.g. on a Wednesday they type
     "週一 排骨飯+1"), the record is written with:
        date:      todayDate   (the Wednesday the order was PLACED)
        dayOfWeek: '週一'        (the Monday the meal is FOR)
     So Date and DayOfWeek disagree (Wednesday vs 週一). This is a defensible
     design (Date = when placed, DayOfWeek = which meal day), and the weekly
     summary correctly keys off DayOfWeek, so aggregation is right. BUT it's a
     trap for anyone reading the Orders tab expecting Date to correspond
     to DayOfWeek, and it means "get my orders for date X" (getUserOrders with a
     date filter) won't find day-prefixed orders placed on other days.
     FIX (design call): Either (a) document clearly that Date=placed-on,
     DayOfWeek=meal-for, and make all user-facing "my orders" queries key
     off DayOfWeek (not Date) for weekly items — which the code mostly does —
     or (b) store an additional MealDate column (the actual calendar date
     of the target weekday) so Date/DayOfWeek/MealDate are all consistent.
     Option (b) is cleaner long-term.

   [MINOR] Weekend fallback: getTodayDayOfWeek() maps 週六/週日 → '週一'.
     Reasonable (schedule is Mon–Fri) but surprising if a user orders on a
     Saturday expecting a Saturday meal — it silently lands on 週一.
     FIX: Surface this in the help text ("週末點餐將歸入週一"), or allow explicit
     週六/週七 targeting if the schedule ever extends.

   [MINOR] The day-prefix regex only accepts 週[一二三四五] (Mon–Fri). A
     "週六 …" or "週日 …" prefix won't match, so it's treated as part of
     the item name (mis-parse). Consistent with the Mon–Fri design but
     worth a comment.

   • doGet() returns a clean JSON health/status payload.
   • Admin UI: onOpen() → onOpenSpreadsheet() builds the menu;
     refreshDailySummary() / refreshWeeklySummary() correctly

     saveMenuItems + setWeeklyScheduleDay, with correct handling of
     the async (promise) vs sync return from fetchStoreMenu.

  ISSUES:
   [MINOR] initSheets() is called on EVERY doPost (line 170). It's
     idempotent (getSheetByName guards), so it's correct, but it re-runs
     the 5× getSheetByName + getDataRange checks on every webhook hit
     after the first. Low cost, but a one-shot "initialized" flag (e.g. a
     Config key) would skip it after first run. Perf nit, not a bug.

   [MINOR] Inconsistent spreadsheet accessor in Code.js: refreshDailySummary
     / refreshWeeklySummary obtain the workbook via getSpreadsheet() (correct,
     respects SPREADSHEET_ID) but then call
     SpreadsheetApp.getActiveSpreadsheet().toast(...) for the toast — bypassing
     getSpreadsheet(). If SPREADSHEET_ID points at a different sheet than the
     "active" one, the toast fires on the wrong spreadsheet (or throws if
     there's no active one in a standalone script). FIX: reuse the `ss`
     already obtained: `ss.toast('…','成功',3)`.

   [MINOR] doPost() swallows all errors into a 200 response
     ({status:'error'}). Returning 200 on error is actually CORRECT for
     LINE (LINE retries on non-2xx, and you don't want a transient handler
     throw to trigger a webhook replay storm), and it logs via console.error.
     So this is defensible — just note it's intentional.

CROSS-CUTTING OBSERVATIONS
================================================================================
1. ARCHITECTURE (strength): The "resolve-from-globals-else-require"
   bootstrap + "attach-to-globalThis + module.exports" dual-export is
   applied uniformly across all 7 modules. This is what makes the
   single-file GAS bundle (dist/Code.gs) and the modular Node test
   harness both work from the same source. Very clean.

2. DUAL-RUNTIME CORRECTNESS (strength, verified): _isGasRuntime() /
   isGasRuntime() correctly detect the environment (presence of
   UrlFetchApp / SpreadsheetApp). All HTTP, sheet, and crypto ops have
   correct GAS + Node branches. The test suite exercising the Node
   path passing 100% confirms the non-GAS branches are sound.

3. SECURITY (mostly strong, one real gap):
   • HMAC-SHA256 webhook signature: CORRECT. Right algorithm, right
     input (raw body), base64 digest, and — notably — the Node path uses
     timingSafeEqual (constant-time), which is the kind of detail people
     forget. The GAS path uses simple === (not constant-time), acceptable
     for GAS since Utilities doesn't expose a timing-safe compare.
   • Secrets handling: CHANNEL_ACCESS_TOKEN / CHANNEL_SECRET /
     SPREADSHEET_ID are read via PropertiesService.getScriptProperties()
     (GAS) or process.env (Node) — NOT hardcoded. Correct, and the
     deployment guide documents setting them as Script Properties.
   • XSS: Low risk — output goes to LINE (Flex JSON / text), not a browser.
     User text is embedded in Flex text components (JSON-escaped by
     JSON.stringify on send), so no classic DOM XSS.
   • INJECTION: The one real gap is the Google Sheets formula injection
     (see SheetService [MAJOR]) — user text starting with "=" is evaluated
     as a formula. This is the highest-value security fix.

4. GAS ENVIRONMENT COMPATIBILITY (strength, verified):
   • SpreadsheetApp: correctly used for openById/getActiveSpreadsheet,
     getSheetByName, insertSheet, appendRow, getRange().setValue,
     getDataRange().getValues, clear, setFontWeight/setBackground,
     getUi().createMenu/addItem/addSeparator/addToUi, prompt/alert/toast.
     All valid GAS APIs, all guarded by isGasRuntime() so Node doesn't
     choke.
   • UrlFetchApp: correctly used with method/headers/payload/
     contentType/muteHttpExceptions, and getResponseCode()/
     getContentText() parsed. muteHttpExceptions:true is the RIGHT
     choice (lets you inspect 4xx/5xx instead of throwing).
   • PropertiesService: correctly used via getScriptProperties().
     getProperty() with the ''/null/undefined guard.
   • Utilities: correctly used for computeHmacSha256Signature.
   • ContentService: correctly used for createTextOutput +
     setMimeType(MimeType.JSON) in doGet/doPost responses.
   • All GAS-specific globals are feature-detected (typeof X !==
     'undefined') before use — no hard crashes in Node.

5. TESTING (strength): The offline suite is genuinely end-to-end —
   it drives real handleTextMessage() calls through the full
   parse → match → addOrder → summary → Flex pipeline using the
   in-memory sheet mock, and asserts on both the captured LINE
   replies AND the resulting sheet state (per-user per-day orders,
   cancellation, grand totals). The UberEats tests verify URL parsing,
   cent→dollar price conversion, extraction, and persistence. This
   is a much stronger test story than "unit tests exist."

6. BUILD/BUNDLE (verified working): scripts/bundle.js concatenates the
   7 src files in dependency order (Config → Line → Sheet → UberEats →
   Flex → Order → Code) into dist/Code.gs. Re-running it reproduces the
   bundle with only the timestamp line changing — confirming src/ and
   dist/ are in sync. Correct file order matters (Config first so CONFIG
   is defined; Code last so it can call into all the others) and it's right.

CONSOLIDATED RECOMMENDATIONS (prioritized)
================================================================================
P0 — Fix before relying on imported UberEats prices:
  1. Harden _convertPrice() (UberEatsService.js). Use the currency arg;
     for TWD treat as cents only when `num>=1000 && num%100===0` (catches 12000/
     13000/3000, spares 1001/1500). Add unit tests for 1001, 1500, 12000, 3000.

P1 — Correctness/robustness:
  2. Resolve the getUserProfile async race (OrderService.js): await the
     profile before the addOrder loop so Orders.UserName is the real
     display name, not '成員'.
  3. Escape formula injection on sheet write (SheetService.js): prefix
     leading "=" in user strings with "'" (or set column format to text).
  4. Loosen + normalize the getMenuItems() restaurant match
     (SheetService.js): trim + casefold both sides; fall back to day-only
     when strict match is empty.
  5. Clarify/fix the Orders Date vs DayOfWeek semantics (OrderService/
     SheetService): document Date=placed-on vs DayOfWeek=meal-for, and/or
     add a MealDate column; ensure "my orders" queries key off DayOfWeek
     for weekly items.

P2 — Hygiene/minor:
  6. Wrap decodeURIComponent in _decodeSlug() with try/catch (fallback to
     raw slug) to survive malformed %-escapes.
  7. In Code.js, use the already-obtained `ss` for .toast() instead of
     SpreadsheetApp.getActiveSpreadsheet() (consistency + avoids wrong/
     missing active sheet).
  8. Optionally gate initSheets() in doPost behind a one-shot
     "initialized" Config flag to skip the 5-tab check after first run.
  9. Remove or wire up the unused _flexIcon/_flexButton/_flexImage helpers
     (FlexMessage.js) for consistency.
  10. Update docs/deployment_guide.md to list the 5th tab (WeeklySchedule) —
      it currently documents only 4.
  11. Rebuild dist/Code.gs (npm run bundle) as the last step before commit so
      the timestamp/content always matches src/.
